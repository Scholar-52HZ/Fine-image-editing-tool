### ADR-001: 采用仓库内文档作为 AI 协作唯一状态信源

- **状态**：已批准 (Approved)
- **日期**：2026-10-14
- **背景与上下文**：
  在现代多智能体与长周期开发中，Chat 上下文窗口易丢失、重置或受会话长度限制。新开启的会话无法感知先前的讨论与隐式共识，容易发生推倒重来、破坏已有架构等问题。
- **决定**：
  将状态完全内嵌到代码仓库中。通过根目录 `AGENTS.md` 规定准入协议，`docs/PROJECT_STATUS.md` 掌控宏观架构与路线图，`docs/DECISIONS.md` 锚定技术决策，`docs/tasks/TASK-*.md` 单独隔离具体工单进度。
- **后果**：
  - 正面：任何 AI 工具接入均可零摩擦了解当前状态与下一步；
  - 负面：每次提交前 Agent 需额外花时间更新工单与状态文档。

### ADR-002: 多 Agent / 多对话并行开发采用 Git Worktree 物理隔离

- **状态**：已批准 (Approved)
- **日期**：2026-10-14
- **背景与上下文**：
  当用户或系统开启多个会话并行开发不同功能（例如一个会话做推理引擎测试，另一个会话做 UI 界面开发）时，若直接在同一工作目录同时写入，会引发严重的文件覆盖冲突与未提交变更破坏。
- **决定**：
  多 Agent 并行模式下必须使用 `git worktree add <path> <branch>` 为每一个并行工单创建物理独立的工作副本。每一个工单生命周期与一个 Worktree 绑定。禁止多 Agent 并发读写同一个未隔离的本地工作目录。
- **后果**：
  - 正面：彻底避免并发文件踩踏与临时状态相互污染；
  - 负面：需要消耗少许额外磁盘空间，开发完成需手动清理已合并的 worktree。

### ADR-003: 抠图算法引擎设计采用“本地离线推理优先”原则

- **状态**：已批准 (Approved)
- **日期**：2026-10-14
- **背景与上下文**：
  市面上许多抠图工具严重依赖第三方商业在线云端 API（如 remove.bg 等），存在网络依赖、隐私泄露风险、API 限额与调用成本过高问题。本项目作为桌面/独立开发工具，核心诉求是高稳定性、隐私安全与零调用费。
- **决定**：
  1. 核心抠图能力必须采用本地离线神经网络推理（首选 ONNX Runtime 推理框架，兼具轻量、跨平台与 CPU/GPU/DirectML 加速支持）；
  2. 算法选型优先考虑当前开源顶级发丝级/高精度通用抠图模型（如 RMBG-1.4 / RMBG-2.0、BiRefNet、MODNet 或 rembg 生态）；
  3. 推理核心模块（`core/engine`）与上层业务/界面必须彻底解耦，对外仅暴露规范的输入输出管道接口（输入原始 Image/Buffer，输出 RGBA Mask/透明底图）。
- **后果**：
  - 正面：用户完全离线可用，数据绝对私密，处理无次数限制；
  - 负面：本地需加载模型权重（数十至上百 MB），需做好低内存机器与不同硬件（CPU/GPU）的兼容性优化。

### ADR-004: 大模型权重与测试数据严格隔离防污染规范

- **状态**：已批准 (Approved)
- **日期**：2026-10-14
- **背景与上下文**：
  深度学习模型权重文件（如 `.onnx`, `.pth`）体积较大，若意外提交到 Git 代码仓库会导致仓库体积急剧膨胀，拉取极慢；同时，抠图测试用的高清输入图片与导出结果也会污染仓库。
- **决定**：
  1. 在根目录 `.gitignore` 中明确排除所有模型权重（`models/`, `*.onnx`, `*.pth`, `*.bin`, `*.safetensors`）；
  2. 明确排除输入输出缓存（`outputs/`, `cache/`, `temp/`）；
  3. 提供自动化权重下载脚本或引导说明，禁止将巨型模型二进制直传进 Git 历史。
- **后果**：
  - 正面：仓库保持精简轻量，克隆与版本控制敏捷高效；
  - 负面：首次运行环境需有自动下载或提供放入权重的说明提示。

### ADR-005: 核心推理引擎采用分层解耦与多模型统一抽象架构 (Engine + Pipeline)

- **状态**：已批准 (Approved)
- **日期**：2026-10-15
- **背景与上下文**：
  GitHub 上存在多种算法方案（如 Bria RMBG 擅长通用与高精度电商、BiRefNet 专精细密发丝与毛发、U-2-Net / Silueta 适合低资源快速处理）。未来项目需要适配 CLI、桌面端 GUI 或 WebUI，若将推理代码与后处理、合成逻辑硬编码在一起，会导致模型切换困难、算法难以扩展。
- **决定**：
  1. 采用双层解耦架构：
     - `core/engine` 专职模型权重加载、ONNX Runtime 会话单例缓存、预处理与核心前向推理；
     - `core/pipeline` 专职模型无关的通用算法，包括 Alpha 遮罩羽化平滑、去杂点噪点、边缘反光色溢净化 (Defringe) 以及透明/纯色/自定义背景合成；
  2. 抽象出统一的 `BaseMattingEngine` 与 `MattingResult` 实体，向上层 UI / CLI 暴露极简的声明式接口；
  3. 支持动态无感热切换模型（默认选用 `bria-rmbg`，可选 `birefnet-general`、`birefnet-portrait`、`u2net`、`u2netp`、`silueta` 等）。
- **后果**：
  - 正面：结构清晰高度解耦，后续增加新模型（如 SAM-Matting、MODNet）或增加 GUI 无需修改核心推理代码；
  - 负面：多引入了一层结果对象封装，但换来了极强的可测性与可扩展性。

### ADR-006: 建立项目内 AI 专属临时调试草稿与生成产物隔离规范 (.ai/)

- **状态**：已批准 (Approved)
- **日期**：2026-10-15
- **背景与上下文**：
  在多智能体协作与迭代测试时，不同 Agent 容易在项目根目录下随意创建 `test.py`、`temp.png` 等临时碎片文件，不仅让工程目录混乱，还容易误提交到 Git 仓库。
- **决定**：
  1. 在项目根目录设立 `.ai/` 规范目录：
     - `.ai/scratch/`：存放所有一次性临时脚本、测试数据与调试脚本；
     - `.ai/artifacts/`：存放所有中间生成的图表、可视化预览图与临时导出样本；
  2. 在根目录 `.gitignore` 中声明 `.ai/`，使所有 AI 临时草稿与中间成果彻底脱敏、与 Git 仓库物理隔离；
  3. 严禁任何 Agent 在根目录随意散落临时文件。
- **后果**：
  - 正面：根目录与代码库始终保持整洁工业级形态，同时多 AI 会话之间能共享调试资产；
  - 负面：Agent 编写临时脚本时必须自觉指定路径到 `.ai/scratch/`。

### ADR-007: 交互形态双轨落地策略：桌面原生客户端 (PySide6) 与本地 WebUI 协同演进

- **状态**：已批准 (Approved)
- **日期**：2026-10-15
- **背景与上下文**：
  在对桌面原生 GUI（方案 A：PyQt6 / PySide6）与本地 WebUI（方案 B：Gradio / FastAPI / Web）进行全方位对比后，明确了两者满足不同核心场景需求：桌面端提供极致的微操（拖拽批量、卷帘对比、发丝手动精修、单文件免安装运行），而 WebUI 提供局域网跨设备无缝共享（手机/平板免装客户端拍照即抠）。用户明确指示：**两套方案未来均需实现**。
- **决定**：
  1. **双轨并进原则**：明确两套方案均为项目的正式交付目标，先后分阶段推进，共同复用底层的 `core/engine` 和 `core/pipeline`；
  2. **演进顺序与阶段规划**：
     - **第一阶段 (TASK-003)**：优先落地 **桌面原生客户端 (PySide6)**，打造沉浸式专业抠图桌面软件，完成拖拽批量、卷帘对比和换底色等高频本地交互；
     - **第二阶段 (TASK-004)**：落地 **本地 WebUI**，基于轻量 Web 框架（如 Gradio / FastAPI）提供浏览器端交互界面，支持局域网设备免安装访问；
  3. **核心层严格中立**：所有核心推理算法、背景合成与后处理逻辑必须全部收敛在 `core/`，UI 层（`ui/desktop` 与 `ui/web`）仅作为纯展示与调度外壳，严禁侵入核心算法。
- **后果**：
  - 正面：兼顾专业生产力工具体验（桌面版）与多终端便携体验（Web 版），最大化复用核心算法资产；
  - 负面：需维护两套不同的 UI 代码层，需要规范公共事件模型与生命周期管理。

### ADR-008: 远程代码仓库配置与代码提交/上传受权准入原则

- **状态**：已批准 (Approved)
- **日期**：2026-10-16
- **背景与上下文**：
  项目已在 GitHub 创建远程托管仓库（`https://github.com/Scholar-52HZ/Fine-image-editing-tool.git`）。在多智能体自主编码场景中，若智能体自动化执行 `git commit` 或 `git push`，可能将未完全审核的代码或临时变更误推送到公共远程分支，造成版本混乱或意外信息泄露。
- **决定**：
  1. 远程仓库地址固定为：`origin -> https://github.com/Scholar-52HZ/Fine-image-editing-tool.git`；
  2. **强制授权红线**：严禁任何 AI 助手（包括当前及未来接手的任何智能体）在未经用户明确同意或指示的情况下擅自执行 `git commit`（本地提交）或 `git push`（远程上传/推送）；
  3. 日常开发时 Agent 仅负责代码编写、测试验证与工作区状态清理，当达到提交阶段时必须先向用户汇报变更并征求用户同意；只有在用户明确确认后，方可由 AI 协助执行提交或推送。
- **后果**：
  - 正面：彻底避免未经审核的代码直接写入版本历史或推送到 GitHub，赋予用户绝对的代码所有权与把关权；
  - 负面：每次提交/推送需多一步向用户确认的交互流程。

### ADR-009: 硬件状态自动探测与主动设备配置规范（默认 CPU，支持 DirectML GPU 加速）

- **状态**：已批准 (Approved)
- **日期**：2026-10-16
- **背景与上下文**：
  在 Intel i5-9300H CPU 软解推理下，单张高精度抠图耗时达 10~20s。本机配备 NVIDIA GeForce GTX 1650 独显（4GB 显存），但由于原推理环境缺少硬件加速支持导致独显闲置。同时，用户明确要求“设计主动配置方案：检测 CPU 和 GPU 状态并提供使用选择，默认 CPU”。
- **决定**：
  1. **DirectML 硬件加速通道**：采用 `onnxruntime-directml`，基于 DirectX 12 统一驱动体系，跨越 NVIDIA / AMD / Intel 显卡无缝开启 GPU 硬件加速，避免了庞大且环境依赖复杂的 CUDA Toolkit 安装；
  2. **硬件探测与解耦工具库**：封装 `core/utils/hardware.py`，支持自动探测 CPU 型号与核心数、独显型号与显存、系统内存容量以及 ONNX Runtime 可用 Providers，并提供进程内缓存与安全超时兜底；
  3. **铁律：默认 CPU，自主选配 GPU**：
     - 系统底层推理引擎 `AutoMattingEngine(device="cpu")`、CLI 命令行参数 `--device cpu`、WebUI 前端单选器等所有入口，首选项与默认值**必须严格为 CPU**；
     - 提供直观的运行状态横幅（Hardware Badge），清晰提示用户当前运行模式、速度预估与显卡就绪状态；
  4. **双轨会话隔离缓存**：推理引擎内部按 `(model_name, device)` 二元组缓存 ONNX Runtime Session，防止用户在 CPU 与 GPU 之间动态切换时发生内存/显存泄露或重复加载开销；
  5. **GPU 显存安全兜底与自动无缝回退机制**：针对体积庞大（如 1GB 的 Bria RMBG 2.0）或在消费级显卡（<=4GB 显存）上可能触发 DirectML 显存不足（`E_OUTOFMEMORY` / `DXGI_ERROR_DEVICE_HUNG`）的模型，底层推理引擎自动捕获 DirectML 异常并无缝安全降级至 CPU 软解完成处理；WebUI 服务层同时封装健全的异常捕获与指引反馈，杜绝前端红屏崩溃。
- **后果**：
  - 正面：实测 DirectML GPU 模式下相比纯 CPU 模式**提速达 10.26 倍**（单图推理平均耗时从 355.8ms 骤降至 34.7ms）；用户享有对算力模式的 100% 自主控制权，且具备自动防崩降级兜底；
  - 负面：首次通过 DirectML 初始化模型会话时有约 1~2 秒着色器预热编译时间，之后每次推理均实现毫秒级响应。

### ADR-010: 三位一体模型资产分层管理架构（内置极轻 + 本地离线优先寻址 + 自建 GitHub Release 镜像加速）

- **状态**：已批准 (Approved)
- **日期**：2026-10-16
- **背景与上下文**：
  1. 深度学习抠图模型体积差异极大（4.5MB ~ 1.0GB），全量打包入库（>2.5GB）会导致应用极端臃肿，且违反 Git 单文件 100MB 限制；
  2. 原方案隐式硬编码依赖原作者 GitHub Releases 下载，在国内网络环境下常遭遇到限速（几 KB/s）甚至连接超时崩溃；更致命的是一旦原作者删库、改版或附件清理，整个抠图工具的在线下载通道将永久失效。
- **决定**：
  1. **极轻基准模型内置（方案 1）**：
     - 将仅 **4.5MB** 的 `u2netp.onnx` 直接内置在项目 `models/` 目录，在 `.gitignore` 中破例保留追踪；
     - 确保任何用户在任何无网环境下克隆或部署项目，均享有 **0 毫秒下载等待、开箱即用** 的秒级抠图能力；
  2. **多级本地优先寻址链（方案 3 离线包解耦）**：
     - 封装 `core/utils/model_manager.py`，并对推理引擎动态注入优先解析钩子；
     - 检索优先级：`项目本地 models/` 目录（最高） -> `系统全局 ~/.rembg/models/` -> `旧版 ~/.u2net/`；
     - 用户从任何网盘或发布页下载独立的 `models_pack.zip` 后，直接解压拷入 `models/` 即可永久全离线免联网运行；
  3. **自有 GitHub Releases 独立托管 + 国内高速镜像加速**：
     - 将大体积模型（`bria-rmbg.onnx`, `birefnet.onnx` 等）托管于用户自己的 GitHub Releases 资产中（`Scholar-52HZ/Fine-image-editing-tool/releases/tag/v0.1.0-models`），实现资产所有权的 100% 自主可控，彻底解除对外部第三方的依赖；
     - 下载时支持自动挂载国内镜像代理（如 `ghfast.top` / `ghproxy.net`），实现国内免代理高速跑满百兆带宽；
  4. **UI 资产可视化与主流程安全防卡顿**：
     - WebUI 新增专门的 **【📦 离线模型管理 (Model Hub)】** 工作台，集中展示模型本地状态、文件位置与一键高速下载；
     - 下拉选单动态渲染实时就绪角标（如 `[✅ 已就绪 (内置)]` / `[⬇️ 未就绪 (需下载)]`）；
     - 抠图核心主流程增加未就绪拦截与温和指引，严禁在点击抠图时隐式插入漫长未知的静默下载卡顿。
- **后果**：
  - 正面：彻底根治了“应用臃肿”、“下载等待漫长”、“原作者源失效”三大行业痛点，兼顾极小安装体积（约40MB）与全离线极端环境可用性；
  - 负面：用户使用非内置的高精大模型前，需在模型管理页主动下载一次，或手动放入离线包。

### ADR-011: 单前端双端同构与全本地纯离线桌面交付架构（FastAPI + Modern Web + PyWebView JS-API 直通）

- **状态**：已批准 / 储备演进 (Approved for Future Phase)
- **日期**：2026-10-16
- **背景与上下文**：
  1. Gradio 作为机器学习原型验证工具，样式定制能力弱、DOM 结构封闭，难以承载现代 UI 高级动效（如 60fps 原图对比卷帘滑块、发光激光扫描线动画、4x~10x 局部发丝悬浮放大镜等）；
  2. 若分别维护 Gradio（Web 原型）+ Qt/PySide6（桌面原生）+ 自定义前端（Web 生产），会导致团队维护 3 套彼此割裂的 UI 体系与事件系统，维护成本呈 300% 倍增，极易产生技术债务；
  3. 用户对桌面软件提出核心刚性诉求：**打包后的应用必须是 100% 纯本地、纯离线运行，绝不允许依赖任何线上云端 API**，断网环境（拔掉网线）下必须能够正常进行 DirectML GPU 显卡加速推理与图片导出。
- **决定**：
  1. **单套前端代码原则 (Single-Frontend)**：
     - 确立“只维护一套现代化高颜值前端 SPA（现代 Web 技术栈 + Tailwind CSS + 动效库）”的终极 UI 架构原则，彻底规避多端重复开发；
  2. **双端无缝分发 (Dual-Distribution)**：
     - **Web 模式**：通过极轻量的本地 FastAPI 异步微服务挂载静态前端，支持本机构造与家庭/办公室内网移动设备共享；
     - **桌面原生模式**：通过 `pywebview` 借助 Windows 10/11 内置的 Edge WebView2 运行时，以轻量原生无边框窗口运行，不占用系统多余体积（相比 Electron 节省 150MB+ 运行时开销）；
  3. **100% 纯本地离线与内存直通机制 (JS-API)**：
     - 桌面打包形态下，前端通过 `window.pywebview.api` 原生内存桥接直调本地 Python 抠图引擎 `AutoMattingEngine`；
     - 运行机制：0 网络端口占用、0 线上 API 请求、0 外部依赖，全量模型权重与显卡计算 100% 封闭在本地进程与显存内部，断网即开即用；
  4. **渐进式演进与测试保留策略**：
     - 尊重用户节奏，当前阶段完好保留现有的 Gradio WebUI（`webui.py`），用户继续基于已有的五大功能工坊进行业务功能、算法表现与模型效果的充分测试验证；
     - 本架构方案作为下一演进阶段的官方技术蓝图与架构准则存档。
- **后果**：
  - 正面：未来仅需维护一套前端代码即可同时交付极具现代美感的网页版与单机桌面版；彻底消除线上依赖与隐私泄露顾虑；
  - 负面：未来 Phase 启动时需构建轻量的前端工程（Vite 打包产物直接嵌入 Python 工程）。

### ADR-012: 电商商品商用图文全链路自动化系统架构（物理双层阴影 + 几何留白规范 + 程序化展台 + 语义排版）

- **状态**：已批准并交付 (Approved & Implemented)
- **日期**：2026-10-16
- **背景与上下文**：
  1. 电商商品去背若仅做简单的纯白/透明硬切，主体会呈现极严重的“浮空贴纸感”，缺乏真实商业摄影棚的光影质感；
  2. 传统纯生成式 AI (文生图) 在商用电商中有致命缺陷：极易篡改商品本身的包装文字、英文 Logo 与精细结构，无法满足商用级交付；
  3. 各大电商平台（天猫 800x800 正方、亚马逊 1000x1000 且主体必须占 85%、小红书 3:4 种草氛围、详情页 750px 流式）规格差异极大，美工人工逐一适配排版工作量巨大；
  4. 用户本地显卡为 NVIDIA GeForce GTX 1650 (4GB 显存)，必须确保在有限显存下实现秒级出图且绝不 OOM 崩溃。
- **决定**：
  1. **主体像素级保真提取原则**：以已交付的 `BiRefNet / RMBG + Defringe`（DirectML 34ms）为基石，100% 锁定商品真实包装与 Logo，严禁 AI 篡改主体几何；
  2. **物理级真实光影发生器 (`core/pipeline/shadow.py`)**：利用模型提取的精确 Alpha 遮罩，通过 OpenCV 形态学运算分别生成贴地接触阴影 (Contact Shadow)、开阔柔光漫反射投影 (Ambient Shadow) 与磨砂镜面倒影 (Mirror Reflection)；
  3. **画布几何自适应与平台规范留白 (`core/pipeline/framing.py`)**：根据目标平台规范（如亚马逊严格 85% 留白与纯白底 RGB 255），自动提取非透明内容 Bounding Box 并等比例缩放与精准锚点对齐；
  4. **3D 程序化商业展台库 (`core/pipeline/podium.py`)**：内置极简大理石圆柱、北欧温润原木托盘、清透水面波纹光影、摄影棚极简几何块，自动与商品底部无缝贴合；
  5. **语义分析与多平台自动排版拼图 (`core/pipeline/copywriter.py` & `core/pipeline/layout.py`)**：通过规则与语义模板，将输入的产品名、功效与受众自动转化为痛点标题、卖点标签与权威背书，并在 PIL 引擎中秒级完成天猫/亚马逊/小红书/详情页多套规格图的自动化排版与 ZIP 打包；
  6. **WebUI 专属工作台集成**：在 `ui/web/app.py` 正式上线 Tab 4 【🛍️ 电商商品智能工坊】。
- **后果**：
  - 正面：彻底打通从“一张实拍图 + 几句文案”到“多平台全套商用级图包”的秒级全自动工作流（单图排版 <0.8秒）；100% 纯本地运行，不依赖云端 API，完全兼容 4GB 显存；
  - 负面：首版展台采用程序化着色渲染，未来若需影视级环境光线追踪反射，可进一步挂接 IC-Light 作为进阶插件模式。

### ADR-013: 产出物项目内原生沉淀原则（严禁将核心设计方案与代码孤立滞留在 IDE Brain 目录）

- **状态**：已批准 (Approved)
- **日期**：2026-10-16
- **背景与上下文**：
  在 Antigravity 等具备内置 Artifact 记忆系统的 AI 编程环境中，系统默认引导智能体将生成的方案输出至 `<appDataDir>\brain\<conversation-id>/` 目录。这导致一个严重漏洞：设计方案与会话 ID 强绑定，一旦会话结束、重置、切换机器或由其他 AI 工具（如 Cursor、Claude Code、Codex）接手，所有关键方案文件在项目仓库中完全不可见，严重违背“项目文件作为唯一记忆载体 (In-Repo Context & Single Source of Truth)”的核心基石。
- **决定**：
  1. **方案原生落盘目录**：在项目仓库内正式设立 `docs/designs/` 作为核心系统方案、架构演进、视觉工作流（如 `ecommerce_v3_director_workflow.md`）的原生落盘目录，受 Git 追踪；
  2. **绝对禁止 Brain 孤岛**：严禁任何 Agent 将设计文档、改版规划或架构图仅写入 IDE 的 Brain 私有目录而不写入项目；
  3. **双写机制 (Dual-Write)**：若 Agent 需要利用 IDE 内置的 Artifact/Generative UI 功能在聊天窗口呈现卡片，必须**首选（或同步）在项目仓库内的 `docs/designs/` 或 `docs/tasks/` 中生成完整实体文件**，绝不允许产出脱离项目物理存储的“Brain 孤儿文件”；
  4. **唯一权威信源**：无论会话如何流转，后续接手 Agent 仅以当前项目目录内的物理文件作为唯一事实标准。
- **后果**：
  - 正面：确保所有设计方案和架构蓝图永久沉淀在项目版本库中，跨会话、跨工具、跨设备永不丢失；
  - 负面：生成方案时 Agent 需规范路径写入 `docs/designs/`。

### ADR-014: 导演级多智能体协同电商视觉工厂与双轨模型网关架构 (本地离线 A 方案 + 通用 API B 方案)

- **状态**：已批准 (Approved)
- **日期**：2026-10-16
- **背景与上下文**：
  1. 用户体验前期生成的电商主图后明确指出痛点：“完全就是抠图然后把字体内容粘贴上去，没有任何美感和智能的体现”；
  2. 针对顶级行业标杆（美妆轻奢丝绸光影、户外折叠椅真实湖光山色与 4 组工艺拆解卡片、CAD 尺寸图）及美图设计室 (DesignKit) 的工作流分析，单线硬编码脚本无法理解场景意境、无法推演分镜镜头、无法感知材质特写；
  3. 用户提出核心创新洞察：“场景背景可以设置为希望场景类型，而非使用场景底图，保留模板中的底部的视角、情绪等等”；
  4. 用户明确要求：**智能体需要同时保留 A、B 两套方案**：既要在本地无网涉密环境下具备 100% 离线运行能力（方案 A），又必须具备统一标准 API 通道以便使用全球最新的前沿 AI 平台（DeepSeek V3/R1、Qwen、GLM、Claude、GPT-4o 等）进行即时效果测试与横向对比。
- **决定**：
  1. **三维解耦工作流原则**：确立“真实商品主体 100% 锁定 × 期望场景类型自由自然语言定义 × 模板传承商业镜头语法（视角流 + 情绪调性 + 叙事节奏）”的核心设计架构；
  2. **双轨智能体中枢架构 (Dual-Track Agent Gateway)**：
     - **方案 A（纯本地离线）**：通过本地 Ollama 驱动轻量多模态/推理模型（如 `qwen2.5:7b`、`deepseek-r1:7b`），100% 离线、零泄密风险、拔掉网线照常运行；
     - **方案 B（统一云端 API 快速评测）**：采用国际通用的 OpenAI 协议规范（Base URL + API Key），支持在 WebUI 随时一键切换 DeepSeek、阿里百炼、智谱开放平台、硅基流动等最新大模型，毫秒级响应并输出连通测速；
     - 上层四大业务 Agent（商品感知、视觉导演、品牌文案、合成排版）面向统一协议编程，底层 A/B 方案无感自由切换；
  3. **分阶段逐步实施路线**：
     - 阶段 1：智能体双轨网关抽象接口与 WebUI 智能体配置/测速面板；
     - 阶段 2：商业摄影导演分镜引擎（全景->特写->微距提示词推演）与商品局部 ROI 自动智能截取；
     - 阶段 3：现代 HTML5/CSS3 + SVG 矢量排版渲染管线（彻底淘汰 PIL 手写贴字，实现美妆丝绸模板与户外 CAD 尺寸标注模板）；
     - 阶段 4：成套 A+/详情页多模块长图流工作台整合与批量导出；
  4. **全量落盘受控**：架构方案物理归档至 `docs/designs/ecommerce_director_agent_system.md`。
- **后果**：
  - 正面：彻底解决传统电商模版工具“背景死板绑定固定底图”的致命缺陷，兼顾 100% 纯本地离线与极速接入前沿 AI 模型评测的双重优势；排版质感直接跃升至顶级商业大牌水准；
  - 负面：系统需引入统一大模型网络请求客户端与 HTML 矢量渲染依赖。

### ADR-015: AI 原生自适应版本流体系（动态双通道 + 门禁式微快照 + 工单快照账本 + 双闸门受控交付）

- **状态**：已批准 (Approved)
- **日期**：2026-10-17
- **背景与上下文**：
  在 AI 自动化与多智能体协作编程中，版本管理面临两大对立矛盾：
  1. 若完全禁止自动 Commit，AI 在长会话中缺乏故障回滚安全网，一旦写崩将导致未提交代码难以精准复原；
  2. 若无节制自动 Commit，则会导致主干分支被碎片化提交严重污染；若擅自自动 Push，则会危及远程 GitHub 生产环境的安全与声誉。
- **决定**：
  1. **动态快慢双通道 (Dynamic Dual-Speed Lanes)**：
     - **极速通道 (Fast Lane)**：单文件/纯文档/修补，免切分支，在当前分支直接轻量规范提交；
     - **沙盒通道 (Sandbox Lane)**：凡涉及任务工单（`TASK-xxx`）与核心重构，自动检出 `task/TASK-xxx` 独立沙盒分支；多任务并行必须使用 `git worktree` 物理隔离；
  2. **三道质量门禁微快照 (Test-Gated Micro-Checkpoints)**：
     - 在沙盒内，只有同时满足“代码无致命语法错”、“暂存区无大权重/敏感配置污染”、“自动化测试 100% 通过”三道门禁，AI 即可零打扰自动打微快照 `checkpoint(TASK-xxx): ...`，建立毫秒级容错救生索；
  3. **工单内快照账本 (In-Task Rollback Ledger)**：
     - 每次快照必须自动在对应 `docs/tasks/TASK-xxx.md` 账本表格登记 Commit 哈希与一键回滚指令，用户说“回退到 CP-x”时秒级精准复原；
  4. **双闸门受控交付 (Dual-Gated Promotion)**：
     - **闸门一（合并审核）**：任务完成经用户明确同意后，执行 `git merge --squash` 将所有零散快照压缩聚合为一条工业级正式大提交，并删除沙盒分支；
     - **闸门二（远程发布）**：**经用户明确同意后**方可执行 `git push origin main`，未获同意严禁擅自上传。
- **后果**：
  - 正面：赋予 AI 沙盒内放手编码与秒级自愈回滚的自由，同时保证主干历史与 GitHub 仓库 100% 具备工业级优雅纯净度；
  - 负面：合并与推送需经历两步受控确认流程。

### ADR-016: 导演级创作采用轻量内部工作流与按需局部重做

- **状态**：方向已确认，待实施；依据用户 2026-10-17“继续按照这个方向优化这个方案，追加重点【轻量化】”指示。
- **背景**：原导演设计已明确商品保真、场景自由、镜头情绪和 A/B 接入，但需补齐执行依赖、故障恢复与资源边界；用户要求保持一键创作体验并强化轻量化。
- **决定**：
  1. 保留 ADR-014 三维解耦与四角色职责。内部使用固定依赖图执行，模块数量由素材和创作计划决定；默认一键生成，按需展开编辑和局部重做，首版不做自由节点编辑器。
  2. 编排使用进程内执行器、版本化数据对象及原子 JSON 清单，图像文件独立存储；编排层新增第三方依赖为 0，不引入重型 Agent 框架或外部调度服务。专业角色不等于多个常驻模型/进程。
  3. 语言规划与图像生成使用独立协议；模型与本地伴侣运行时外置，按能力调用，本地模式不自动回退云端。主程序不自动下载或启动大型伴侣。
  4. 按依赖失效支持局部重做，保留不可变源资产及版本记录，处理锁定冲突、外部任务未知状态、调用预算与取消边界。
  5. 新版 HTML/SVG 负责排版，Pillow/OpenCV 继续承担图像处理。渲染分发需先做原型验证；运行库、字体、渲染器及模型都计入分层体积报告，不将历史“几十 MB”愿景视作完整安装包的已验证保证。
  6. 轻量化预算和验收记录于 `docs/designs/ecommerce_director_agent_system.md` 第 3 节；预算是待实测目标，不能牺牲保真与视觉质量来静默达成。
- **边界**：不改变 ADR-011 的未来双端方向；外部伴侣与桌面“0 端口”的适用关系另行决策。生图提供方、渲染运行时尚未选定，本 ADR 不授权引入具体新依赖。
- **后果**：可在保持一键体验的同时减少无效调用、重复大图与返工；需要实现产物引用、失效规则和恢复检查。设计方向确定不代表功能已交付。
