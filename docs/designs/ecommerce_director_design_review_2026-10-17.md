# 导演级电商视觉工厂设计复审与优化建议

> 日期：2026-10-17。状态：评审建议，尚未替代已批准设计或 ADR。
> 后续处理：用户已指示按“一键创作、内部工作流、局部重做、轻量化”继续优化。相关契约已纳入 [v3.1 主方案](ecommerce_director_agent_system.md) 与 ADR-016；本文保留为修订前的评审证据，具体服务商、渲染运行时和桌面端口边界仍待决策。
> 依据：`ecommerce_director_agent_system.md`、v2/v3 工作流方案、TASK-007、ADR-011/012/014，以及现有图像管线与 WebUI 服务代码。
> 范围：检查设计完整性和工程可执行性。本轮没有实现新功能，没有验证真实模型出图质量，也没有看到旧文档引用的“参考图一/二”实体素材。

## 1. 结论

“真实商品资产 × 自由场景 × 模板镜头与情绪”值得保留，A/B 外部服务接入和本地合成的边界也合理。但现方案仍是愿景与模块清单，缺少从分镜到背景图、从真实素材到可执行镜头、从排版到视觉验收的关键契约。直接按现有四阶段顺序实现，容易先做出配置面板，最后才发现成图链路不能闭合。

建议先补齐下表 P0 项，再用一张商品图、一套风格、一张主图完成垂直闭环。四个业务角色可保留，首版由固定流程调度，不必引入开放式多 Agent 自主协商。

## 2. 问题、影响与建议

### P0-1：背景生成能力缺失，语言网关无法覆盖完整流程

**位置**：原设计第 2、3、5 节。`BaseLLMClient` 只有对话与诊断；图中“场景生成”没有对应客户端、输入输出或验收项。v3 工作流提到外部生成工具，但没有接回当前任务。

**影响**：导演可以输出提示词，却无法据此取得可用于合成的背景图。对话接口连通不等于生图能力可用。

**建议**：保持 LLM 网关，另定义图像服务协议，不强行用同一种网络接口统一所有服务。能力按 `text / vision / structured_output / image_generation / masked_edit` 声明并探测。图像任务定义提交、查询、取消、取回资产；同步提供方也适配成同一种业务任务结果。

图像请求至少携带：场景描述、画布尺寸、主体占位区域、支撑平面/地平线、光向、文字安全区和可选 seed；结果记录实际尺寸、提供方、任务 ID、生成参数及资产来源。首版先支持空场景背景生成与本地回贴真实主体，掩膜编辑作为可选能力。若缺少生图能力，允许使用用户背景或本地背景完成合成，但明确降级，不能显示“自由场景生成成功”。

### P0-2：镜头自由度与真实商品保真之间缺少执行约束

**位置**：原设计核心原则、第 3 节；v3 工作流中的 45° 微距、手持、折叠和使用态。

**影响**：单张正面图只能提供已拍到的信息。改成侧面、打开状态或手持遮挡会需要补造商品内容，违反保真目标；裁剪放大也不能还原原图中不存在的微距细节。

**建议**：每张素材登记 `asset_id`、视角、状态、像素尺寸、可用 ROI 和来源。每个镜头必须引用真实素材 ID 与裁剪框；规划前先判断素材是否满足镜头条件。缺图时改用已有视角、要求补图或跳过模块。ROI 用统一归一化坐标并校验边界、最小有效像素及与主体遮罩的交集，低可信结果允许用户调整。

保真验收应定义为“不生成或替换商品结构、Logo 与包装文字；所有几何变换可追溯”。原图与原始抠图资产不可变；缩放后的合成层按明确变换核验，不能与原图直接逐像素比较。`refine.py` 的去色溢会修改边缘 RGB，重打光也会改色，因此记录处理范围并允许关闭；不可笼统承诺整幅像素 100% 不变。透明瓶体、反射金属等先列为需要人工检查的困难样本。

### P0-3：多模态、结构化输出和错误契约不足

**位置**：原设计第 2.1 节的 `messages: list[dict] -> str` 与 `json_mode: bool`。

**影响**：没有统一图片编码和资产引用；字符串结果无法可靠连接裁剪、灯光和排版执行；JSON 格式合法也可能字段错误、引用缺失或坐标越界。不同平台与模型不能仅凭 Base URL 推定能力一致。

**建议**：采用带版本的请求/结果对象。明确文本、图片内容块、超时、取消、请求 ID；返回解析数据、模型标识、耗时、用量（不可用则为空）、结束原因与标准错误类型。结构化结果做 schema 校验及业务校验；失败时最多进行有界修复，仍失败则保留可编辑草稿，阻止执行无效计划。

Ollama 的视觉调用需要支持视觉的模型及图片输入，REST 图片通过 `images` 传递 base64；结构化输出可传 schema，但仍应在应用端校验。[视觉官方文档](https://docs.ollama.com/capabilities/vision)、[结构化输出官方文档](https://docs.ollama.com/capabilities/structured-outputs)。据此，本项目应将“对话测试”“看图测试”“结构化测试”分开，不能用一次问候请求代表全能力验证。

### P0-4：商品事实、尺寸和营销创作没有隔离

**位置**：原设计的参数表、CAD 尺寸图和品牌文案角色；现有 `copywriter.py`。

**证据**：现有规则会补写“官方正品保障”“严苛品控检测合格”“真实口碑认证好评”等输入中未提供的信息。未来若直接让模型扩写，问题会进入整套模板。

**建议**：建立 `ProductFacts`，字段记录值、单位和来源；视觉观察只能是候选推断，不能自动升级成已证实参数。尺寸图仅使用用户提供或确认的尺寸，缺失则省略标注；没有标定数据时不从单张图片计算真实毫米尺寸。促销、认证、测试结果、功效数据必须有输入依据；创作只改写表达，不补造事实。

### P0-5：离线、云端和未来桌面约束需要明确兼容范围

**位置**：原设计第 2 节与 ADR-011/014。

**影响**：默认云 API 与“离线运行”不是同一个运行状态；本地 Ollama/ComfyUI 的 HTTP 接入又与 ADR-011 的“0 网络端口”字面约束存在待澄清之处。当前不能宣称完整导演流程已满足桌面离线交付。

**建议**：区分基础抠图离线、外部本地 AI 服务、云端 AI 三种能力组合。严格本地模式禁止云端回退和外部素材请求；字体、图标与模板均使用本地资源。外部服务不就绪时保留抠图与本地合成。明确图片发送到哪个服务，并以任务配置快照固定目的地；任务执行中切换设置不改变已运行任务。

API Key 默认从环境变量读取或仅保存在会话内；非敏感配置可以 JSON 持久化。若需要“记住密钥”，再确定操作系统凭证存储方案。脱敏显示不能替代存储保护。局域网共享时配置入口与用户任务必须隔离，避免全局配置导致另一会话使用错误凭证。渲染器只接收受控模板和经过转义的数据，不执行模型返回的 HTML、脚本或任意本地路径。

“0 端口”是否仅指桌面主程序不自建服务，还是也排除伴侣服务，需在进入桌面阶段前由用户澄清并记录 ADR；本次不修改原决策。

### P1-1：模板需要成为构图与风格规范

**位置**：原设计第 4 节。目前主要列出 HTML 文件、字体和视觉元素。

**影响**：替换渲染工具仍可能产出“主体加标题”的旧效果；各 Agent 独立生成也可能造成同套图片色彩和光向冲突。

**建议**：每个模板附带 `TemplateManifest`：适用品类、所需视角、模块顺序、主体区域、文字安全区、标题行数/字数、字体层级、色板、光向和不适用条件。整套图片共享 `StyleSpec`，模块只允许在约束内变化。分镜和文案可并行，但必须读取相同风格与事实快照，汇合后检查冲突。

先检查背景的地平线、支撑面和留白是否匹配，再做主体合成。用户预览后可以锁定场景、商品位置、文案或模块，后续只重做未锁定部分。审美验收至少检查：主体焦点、透视接触、光向、文字节奏和成套一致性。

### P1-2：渲染器和交付体积仍未做技术验证

**位置**：原设计第 4 节的“无头 Chromium 或轻量矢量引擎”“4K/300 DPI”“几十 MB”。

**影响**：两条渲染路线并非默认等价；浏览器与字体的分发也必须计入安装体积。DPI 元数据不能增加像素细节，CAD 箭头绘制精度也不能证明商品尺寸准确。

**建议**：先做相同模板的渲染验证，比较中文字体、SVG、阴影、图片透明度、离线打包、内存与安装体积，再选唯一主路线。Playwright 官方提供页面、区域和整页截图能力，可作为候选验证手段，但这不证明已满足桌面打包约束。[官方截图文档](https://playwright.dev/python/docs/screenshots)。

验收写清输出宽高、色彩模式、字体加载成功、无溢出、无丢图；预览和最终导出共用模板。4K 需定义具体规格与输入像素门槛，低分辨率素材标注放大情况；长图按模块渲染后拼接，设置最大尺寸与内存预算。本地图像裁剪、Alpha 合成、缩放和编码仍可复用 Pillow/OpenCV；HTML/SVG 负责新版排版，不必删除有效的底层图像能力。旧版电商路径在新版验收前保留。

### P1-3：缺少任务恢复、成本控制与可复现记录

**位置**：原设计第 3、5 节；现有 `process_ecommerce_suite` 是同步整体调用，出错后返回整体失败。

**建议**：固定执行图：素材检查 → 事实与风格 → 分镜/文案 → 计划校验 → 背景 → 合成 → 排版 → 检查 → 导出。四个角色可以由少量调用实现，裁剪、校验、合成不需要由模型临时决策执行代码。

按任务保存配置、素材哈希、模型/模板/提示词版本、生成资产和各阶段状态。任务 ID 使用 UUID；各模块可单独重试，改变文案只重排版。显存任务默认串行，文本请求限并发；设调用次数、时间和费用预算。网络超时后的付费生图可能已经在服务端完成，应先查任务状态；仅在提供方支持时使用幂等键，不能盲目重发。相同 seed 也不能保证跨模型、跨版本复现，已生成图片本身必须保留。

### P1-4：现有测试不覆盖未来视觉目标与性能承诺

**位置**：原设计中的“34ms”“毫秒级响应”“商业大片”和 TASK-007 验收项。

**建议**：将历史特定硬件/模型测试与未来服务指标分开，记录冷启动/热运行、模型、输入尺寸、预处理、推理、生成和导出的各段耗时。报告成功率、重试次数及端到端耗时，不把单次本地推理速度用于云生图或整套交付承诺。

建立用户认可的固定样本集：美妆瓶体、反光包装、户外装备、低分辨率输入及细节不足的素材。自动检查尺寸、字体、越界、素材引用和事实来源；人工比较构图、接触感、商品辨识度和套图一致性。模型自评分只供参考。当前 34 项测试通过不能证明导演方案视觉质量达标；原参考图应落入项目资产并记录可用范围，不能只引用会话中的“图一/二”。

## 3. 建议的数据流与最小契约

```text
真实素材 + ProductFacts + 用户场景 + TemplateManifest
  → 素材可执行性检查
  → StyleSpec + ShotPlan[] + CopyBundle
  → schema / 素材引用 / 事实 / 坐标校验
  → 用户可编辑预览计划
  → 背景服务 → 本地主体合成 → 受控模板渲染
  → 自动检查 + 用户视觉检查 → 成套图片 / ZIP / 任务清单
```

建议字段（为待实现契约，不是现有代码）：

| 对象 | 最小字段 |
| --- | --- |
| ProductAsset | asset_id、文件哈希、原始宽高、视角/状态、mask 引用、可用 ROI |
| ProductFacts | 产品名、属性值/单位、source、confirmed；未知值为空 |
| StyleSpec | style_id/version、色板、光向、字体层级、留白规则、情绪 |
| ShotPlan | shot_id、asset_id、crop_xyxy、主体目标区域、背景描述、template_id、事实引用 |
| JobSnapshot | job_id、schema_version、配置引用、模板/提示词版本、预算、逐阶段状态 |
| RenderArtifact | 模块 ID、实际尺寸、文件哈希、输入引用、处理记录、检查结果 |

所有坐标必须声明坐标系；执行前转换为像素并校验。凭证不写入任务快照和 ZIP。首版可用任务目录和 JSON 清单，无需先引入数据库或重型 Agent 框架。

## 4. 实施顺序与验收关口建议

保持 TASK-007 四阶段框架，补齐各阶段交付边界：

1. **阶段 1 前置契约**：确认能力矩阵、图片/结构化协议、图像服务协议和保真范围。网关除连通外，还验证超时、能力不匹配、脱敏、无效输出和本地模式禁止外发。
2. **阶段 2 垂直闭环**：一张真实商品图、一套风格、一张主图；可从场景描述获得真实背景资产，使用原视角合成，形成可编辑计划及成图预览。此时提前做一个最小模板验证，降低后期返工。
3. **阶段 3 质量闭环**：确认渲染分发路线，完善美妆/户外模板及视觉样本集，加入缺素材降级、事实溯源、尺寸来源、字体/溢出检查。固定样例由用户评审后再扩大模板数量。
4. **阶段 4 成套交付**：1~6 张素材映射、模块选择、局部重做、任务恢复、预算限制、套图风格检查和 ZIP。桌面打包继续归属未来阶段，不在本轮同时重构前端。

## 5. 决策边界与本轮交接

- 本次完成设计复审，未改动业务代码、依赖或已批准 ADR。
- P0 项优先进入设计修订；具体图像提供方、渲染运行时及桌面端口边界仍需形成正式决策，不能把本评审当作已经批准的新架构。
- 下一步：将 P0 契约整理到主方案与 TASK-007 验收项，再开始阶段 1；保留现有本地抠图和旧版电商能力。
- 验证方式：核对原方案、工单、代码证据与官方能力文档；检查本评审的本地引用和结构。未重跑算法测试，沿用 2026-10-16 的 34 项通过记录作为历史基线。
